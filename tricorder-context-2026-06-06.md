## The design discussion (completed this session)

### Starting point
Issue #22 proposes "Tricorder: Progressive Discovery and Organizational Learning System" — a significant expansion from dbt/SQL-specific tool to a general-purpose repository learning system with a 6-level progressive trust model.

Full vision: https://github.com/dhk/tricorder/issues/22

### Key decisions made

**Q1: Lens selection**  
Auto-detect repo type, propose the most likely lens (e.g. analytics-engineering), let user select an alternative. Not user-configured from scratch.

**Q2: Level 0/1 purpose**  
The pre-credential phases (local filesystem + git history analysis) are the product's trust funnel — "am I willing to invest more trust and time in this product?" — not just a technical step. They're part of the user journey, not standalone utility.

**Q3: Artifact storage**  
User-selectable, config-driven. Default: `.tricorder/` in the current directory (i.e., inside the repo being analyzed when running from it). Falls back to external cache. Best practice: use current dir if possible, but follow XDG conventions. Store location choice in config.

**Q4: Command rename**  
Yes, rename. Old → New:
- `ready` → absorbed into `discover` output
- `probe` → keep (cost planning tool)
- `harvest` → `analyze`
- `synthesize` → `learn`
- `render` → keep or rename to `build` (TBD)
- New: `discover` (Level 0+1, no credentials)

**Q5: Scope approach**  
Agreed on **"principled evolution" (Option A with one Option B idea borrowed)**:
- Remap existing commands to new vocabulary
- Add `discover` as genuine new front-end (local + git, no creds, detects lens)
- Borrow artifact contract from Option B: each command writes structured output that the next command reads
- Keep current synthesis internals intact — dbt/SQL becomes the analytics-engineering lens
- Defer separating `learn` and `interpret` into distinct phases until second repo type is validated
