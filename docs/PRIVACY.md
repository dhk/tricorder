# Privacy and data flow

Tricorder processes code-review records that may be private, personally identifying,
or sensitive. This document describes the shipped behavior; it is not a promise that
generated output is anonymous or safe to publish.

## Data flow

| Stage | Reads | External recipient | Local writes |
|---|---|---|---|
| `discover` | repository files | none | profile and fingerprint under `.tricorder/` |
| `discover --history` | local git log and paths | none | contributors, hotspots, timeline |
| `analyze` | GitHub PR metadata, bodies, reviews, inline comments, identities, paths, selected context files | GitHub API | structured artifacts and raw caches |
| `learn` | Level 2 records and repo context | configured Anthropic or Gemini API | named learnings, profiles, and raw LLM responses |
| `interpret` / `improve` | earlier generated artifacts | configured LLM API | interpretations and roadmap |
| `build` | local learning artifacts and optional name map | none unless the user later publishes/serves them | `explorer/data.js` |

## GitHub access

Authentication is resolved from `GITHUB_TOKEN`, `gh auth token`, or supported macOS
Keychain items. Tricorder asks GitHub for repository and pull-request data using that
identity. A credential that can access private repositories allows Tricorder to read
their review history too. Use least privilege, confirm the target `OWNER/REPO`, and
apply organization SSO restrictions where applicable.

`analyze` does not write to GitHub. Other optional functionality such as
`improve --forge` is a separate workflow that can create branches, issues, or pull
requests and should be authorized separately.

## LLM transmission

LLM-backed levels transmit content required by their prompts to the selected
provider. This includes PR titles/descriptions, review and inline-comment bodies,
file paths, reviewer and author logins, extracted patterns, and repository context.
The provider receives this material under the user's provider account and settings.
Tricorder cannot override provider retention, training, regional, or contractual
terms. Verify those terms before analyzing confidential or regulated material.

Named reviewer fingerprints and author growth profiles are generated by default and
can affect people if misread. They are probabilistic summaries of observed review
records, not performance evaluations or complete accounts of someone's work.

## Local caches

Artifacts live under the analyzed repository's `.tricorder/` directory, generally
in a per-repository `OWNER__REPO/` subdirectory. `.raw/` can retain fetched review
records and intermediate LLM responses to support incremental and resume-safe runs.
Optional reports may be written elsewhere via `--out`. Legacy v1 scripts can also
use `~/.learn-from-work/cache/`.

These files are plaintext. Filesystem permissions, backups, sync tools, indexing,
and endpoint security determine who else can read them. Keep `.tricorder/`, reports,
name maps, and `explorer/data.js` out of commits unless deliberately reviewed for
publication. Delete the specific cache and report paths when retention is no longer
needed.

## Visibility modes

`tricorder learn --visibility` controls the optional Markdown report, not collection,
LLM transmission, or the complete artifact set:

- `private` includes named reviewer and author profiles;
- `team` omits author profiles but retains named reviewer material;
- `public` omits author profiles but does not comprehensively anonymize all content.

Named profiles and identities remain in `learnings.json` and raw caches in every
mode. Do not treat `team` or `public` as a security boundary.

## Name maps and anonymization

`tricorder build` can replace exact login strings using a JSON name map. Keep the
map private because it is the re-identification key. This substitution is
pseudonymization, not guaranteed anonymization: quoted text, repository names, file
paths, dates, role descriptions, rare incidents, and small-team context can identify
people or disclose private work.

Before sharing, inspect every generated field, remove unnecessary evidence, confirm
consent and policy, and test the result as if viewed by someone who already knows the
team. Never publish directly from a private cache.

## Publication risk checklist

- Confirm the source repository permits reuse of its review data.
- Remove tokens, secrets, private URLs, customer data, and proprietary code excerpts.
- Remove or generalize contributor identities and uniquely identifying context.
- Review quotations, file paths, repository names, dates, and small-group findings.
- Confirm the explorer's embedded `data.js`, not only its visible default tab.
- Publish to an access-controlled location unless the output was explicitly cleared
  for public release.

If exposure occurs, stop serving the artifact, rotate any exposed credentials,
remove published history where possible, and follow [SECURITY.md](../SECURITY.md).
