# Tricorder repository lenses — research findings

**Date of research:** 2026-09-02. All URLs retrieved 2026-09-02 unless noted otherwise.
**Test case:** `block/berd` (public, Tauri 2 + React 19 desktop app; fingerprint per the Part 3 data, collected 2026-09-02).
**Companion artifacts:** `product-engineering-desktop.yaml`, `platform-engineering.yaml`, `detection-rubric.yaml`.

A note on naming: "Tricorder" is also the name of Google's program-analysis platform (Sadowski et al., ICSE 2015, cited in Q4). Nothing in this document depends on Google's tool; the citations there are about the practice of surfacing analysis in code review, not about the user's product.

## Q1

**Question:** accepted methods and reference implementations for determining what a repository is from its contents alone, with no execution.

| Entry | What it is | Tricorder concept overlap | Verdict |
|---|---|---|---|
| GitHub Linguist (`languages.yml`, strategy pipeline, exclusions) | The reference implementation of content-based language detection: ordered strategies (modeline → filename → shebang → extension → XML header → manpage → heuristics → naïve Bayes), with binary, vendored, generated, documentation, and `data`/`prose` languages excluded from statistics | Detection signals; composition_check | adopt/reference |
| Linguist overrides (`.gitattributes`: `linguist-vendored`, `linguist-generated`, `linguist-documentation`, `linguist-language`) | Maintainer-declared per-path overrides that Linguist honors before classification | Detection signals (repo self-declaration beats inference) | adopt/reference |
| go-enry | A Go port of Linguist using the same `languages.yml` data; exposes per-file language guessing plus vendored/binary filtering as a library | Detection signals (embeddable alternative) | differentiate |
| Ecosystem manifests: `package.json` (npm), `Cargo.toml` (Cargo), `pnpm-workspace.yaml` (pnpm) | Authoritative, machine-read ecosystem indicators. `package.json` is required for npm packages; `Cargo.toml` is the required per-package manifest; `pnpm-workspace.yaml` defines a pnpm workspace root | Detection signals (high-weight positive evidence) | adopt/reference |
| Framework config files (`tauri.conf.json`, `vite.config.ts`, `playwright.config.ts`, `biome.json`) | Framework-mandated files; `tauri.conf.json` is generated by `tauri init` and lives in `src-tauri/` — near-definitive for a Tauri app | Detection signals | adopt/reference |
| AI-assistant configuration (`CLAUDE.md`, `AGENTS.md`, `.agents/`, `.cursor/`) | `AGENTS.md` is an open format self-reporting adoption by 60,000+ open-source projects; these files say nothing about the host repository's code archetype | Detection signals — global exclusion list | ignore |
| Community-health files (`SECURITY.md`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `CODEOWNERS`) | GitHub-recognized governance/community files that appear in repositories of every kind | Detection signals — global exclusion list | ignore |

**Notes**

**Direct answer.** The accepted method, as implemented by Linguist and inherited by every comparable tool, is: (1) enumerate files; (2) exclude binary, vendored, generated, and documentation paths plus maintainer overrides; (3) classify each remaining file via an ordered cascade of increasingly fuzzy strategies (explicit override → modeline → known filename → shebang → extension → content heuristics → Bayesian classifier); (4) aggregate to repository level as byte shares per language. Tricorder should copy this shape exactly: deterministic, content-only, no execution, exclusion-first, and maintainer-overridable.

**Authoritative vs. weak indicators.** Strong ecosystem indicators are files a tool *requires*: `package.json` (npm), `Cargo.toml` (Cargo), `pnpm-workspace.yaml` (pnpm workspace root), framework configs like `tauri.conf.json` / `vite.config.ts` / `playwright.config.ts`. Weak indicators are files that appear everywhere regardless of archetype: `README.md`, `LICENSE`, `CHANGELOG.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `Dockerfile`, `.github/workflows/*.yml`, and now AI-assistant files (`CLAUDE.md`, `AGENTS.md`, `.agents/`, `.cursor/`). Weak files must be excluded from archetype inference — not merely downweighted — because a desktop app (the test case) carries eleven of them.

**Monorepos and polyglot repos.** Linguist does not partition: it classifies per file and aggregates bytes over the whole repo, so a polyglot monorepo shows up as multiple language bars, not multiple labels. Partitioning in practice is done by workspace manifests (`pnpm-workspace.yaml`; Cargo workspaces; npm `workspaces`), by per-path ownership (CODEOWNERS), and by catalogs that register *multiple components per repository* (Backstage `catalog-info.yaml` locations and `spec.subcomponentOf`; see Q2). Consequence for Tricorder: detect composition per *path*, select the lens at repo level, and let `file_tags` carry the per-path nuance into Phase 1 rather than trying to assign one language to the repo.

## Q2

**Question:** is the five-way partition defensible and specific enough, and where does `block/berd` land?

| Entry | What it is | Tricorder concept overlap | Verdict |
|---|---|---|---|
| Backstage component types (`service`, `website`, `library` well-known values, open `spec.type`) | The most widely deployed software-catalog taxonomy; kinds (Component/API/Resource/System) with a small, deliberately extensible type vocabulary | Archetype taxonomy; sub-profile split | adopt/reference |
| Backstage system model (`subcomponentOf`, systems, multiple components per repo) | Catalog model that treats a repository as host to *several* typed components | Mixed-repository handling (Q6) | adopt/reference |
| crates.io category list | Registry self-classification (e.g., "Command line utilities", "Web programming", "GUI"); maintainer-assigned, up to 5 per crate, unvalidated | Archetype taxonomy | differentiate |
| SLSA (Supply-chain Levels for Software Artifacts) | An assurance-level framework (build integrity, provenance), not a classification of repository *type* | Maturity ladder analog (Q4); platform lens authority | differentiate |
| OpenSSF Scorecard checks | 18 cross-cutting security-hygiene checks (branch protection, pinned dependencies, signed releases, token permissions…) applicable to any OSS repo | Tooling gates; platform lens axes — not an archetype | differentiate |

**Notes**

**Direct answer.** The five-way partition is defensible as a top-level split only if `product-engineering` is treated as a *parent* with sub-profiles. The published evidence supports this: Backstage — the reference taxonomy for "what kind of software is this" — ships exactly three well-known component types (`service`, `website`, `library`) and explicitly expects organizations to extend the vocabulary, because tooling behaves differently per type. Review concerns differ just as much: a desktop app review cares about IPC trust boundaries, packaging, signing, and telemetry (Q3); a backend service review cares about API contracts, authn/z, data migrations, and observability; a library/SDK review cares about API stability and semver; a CLI review cares about flag UX, exit codes, and shell integration. One `product-engineering` lens cannot carry all of those axis sets without going vague — and vagueness is exactly the failure mode this research is meant to remove.

**Recommended split.** Keep the five top-level archetypes; under `product-engineering` define sub-profiles `product-engineering-desktop`, `product-engineering-mobile`, `product-engineering-backend-service`, `product-engineering-library`, `product-engineering-cli`. Sub-profiles inherit the domain-neutral category core (Q5) and add their own axes and authorities. This mirrors Backstage's "small core, open extension" design instead of registry-style free-for-all categories (crates.io's list is maintainer-assigned and unvalidated — useful as hints, not as ground truth).

**Where Berd lands.** `product-engineering-desktop`. Decisive evidence: `src-tauri/tauri.conf.json` present (referenced in the README's `externalBin` staging instructions); `index.html` + `vite.config.ts` + `src/**/*.tsx` (React webview frontend); TypeScript 76.3% and Rust 18.9% of bytes; the README self-describes "Berd is an open-source desktop app… built with Tauri 2 and React 19". Note the trap: Berd's *product domain* is AI agents ("a desktop app for getting work done with any model"), and it ships `skills/`, `.agents/skills/`, `AGENTS.md`, `CLAUDE.md`. That makes the *subject matter* agentic, not the *code archetype* — the review rubric for its codebase is the desktop-app rubric. Archetype describes the artifact being engineered, not what the artifact does.

**Citations**

- *Descriptor Format of Catalog Entities* — Backstage (CNCF), https://backstage.io/docs/features/software-catalog/descriptor-format/ — retrieved 2026-09-02. Supports: well-known `spec.type` values `service`, `website`, `library`; the type field is required but open, and "an organization should take great care to establish a proper taxonomy"; tools may behave differently per type.
- *System Model* — Backstage (CNCF), https://backstage.io/docs/features/software-catalog/system-model/ — retrieved 2026-09-02. Supports: components as pieces of software (mobile feature, website, backend service, data pipeline), composed into systems; one repository can host multiple typed components.
- *Categories* — crates.io (Rust project), https://crates.io/categories — retrieved 2026-09-02. Supports: registry categories are flat, maintainer-chosen, and numerous (e.g., "Development tools", "Command line utilities", "GUI") — a signal vocabulary, not a validated taxonomy.
- *SLSA* — OpenSSF, https://slsa.dev/ — retrieved 2026-09-02. Supports: SLSA is a framework of *levels of increasing assurance* for supply-chain integrity — an axis of maturity, not a repository type.
- *Scorecard checks documentation* — OpenSSF, https://github.com/ossf/scorecard/blob/main/docs/checks.md — retrieved 2026-09-02. Supports: 18 automated, cross-cutting security checks (Dangerous-Workflow, Token-Permissions, Pinned-Dependencies, Signed-Releases, Code-Review, etc.) usable as deterministic gates regardless of archetype.

**Notes**

**Direct answer (Berd / product-engineering-desktop).** The primary-source set a Tauri-desktop reviewer would recognize decomposes into five clusters:

1. **Shell and trust boundary (Tauri).** Tauri's own security docs define the reviewable unit: the IPC layer is *the* trust boundary; commands must be validated; capabilities (files under `src-tauri/capabilities/`) scope what each window/webview may invoke; permissions can deny commands and map scopes; CSP in `tauri.conf.json` constrains the WebView. Review dimensions: command input validation, capability minimality, permission scoping, CSP presence and tightness, remote-URL exposure.
2. **Rust core.** Rust API Guidelines (API shape, documentation, future-proofing), Clippy catalog (machine-checkable idiom), Rustonomicon (`unsafe` soundness and justification), cargo-deny/cargo-audit (license/advisory/ban enforcement), cargo-geiger (`unsafe` accounting in the dependency tree). Review dimensions: idiom, `unsafe` justification, dependency hygiene.
3. **TypeScript/React frontend.** Rules of React and Rules of Hooks (normative, from the React team), typescript-eslint (type-aware rules), Biome catalog (the tool Berd actually runs). Review dimensions: hook discipline, effect purity, type safety (`any`/casts), state immutability.
4. **Desktop-specific concerns a service lens misses.** Tauri bundler config (`externalBin` sidecars must exist per target triple — Berd stages `goosed`), per-platform config merges, macOS signing/notarization, Windows signing, updater signature requirement, release channels, telemetry (Berd publishes a `TELEMETRY.md` policy), accessibility (WCAG 2.2 applies to WebView UI).
5. **E2E testing.** Playwright's own best practices (locators, web-first assertions, isolation, CI, linting tests). Berd's PR template's Testing section (before/after screenshots or recordings for UI changes) is the team-level convention that sits on top.

**Direct answer (platform-engineering).** A platform/infra reviewer recognizes GitHub's own Actions hardening guide (token permissions, OIDC, action pinning, `pull_request_target` dangers), OpenSSF Scorecard's 18 checks (each with remediation docs — the closest thing to a published "deterministic review" catalog), and SLSA (provenance and build integrity levels). OWASP ASVS is authoritative but scoped to web apps/services; it belongs to a future `product-engineering-backend-service` sub-profile, not the platform lens. No comparable primary standard exists for general infrastructure-as-code review; that gap is recorded in `## Open gaps`.

**Notes**

**Direct answer — the mapping.** Published practice supports the ladder rather than replacing it. Recommended mapping: `warn`-level tooling ≈ `convention`/`rule` boundary; `deny`/`forbid` in CI or a required check = `deterministic`; documented-but-unenforced = `rule`; unwritten team habit = `convention`; one-off reviewer catch = `judgment`. Google's "project customization, not user customization" principle is also the correct governance rule for lens selection: the *repository* (via its config files and overrides), not the end user, should steer detection.

## Q5

**Question:** published taxonomies of code-review comments, and whether to use one domain-neutral taxonomy with per-lens extensions or a fully per-lens enum.

|---|---|---|---|
| Mäntylä & Lassenius (2009), *What Types of Defects Are Really Discovered in Code Reviews?* (TSE) | Peer-reviewed defect taxonomy from 32 review sessions: functional vs. evolvability defects; ~75% of findings were evolvability (documentation, structure, readability) | Category enum (core split) | adopt/reference |
| Beller et al. (2014), *Modern Code Reviews in Open-Source Projects: Which Problems Do They Fix?* (MSR) | Replicated the finding in OSS: a "strikingly similar… 75:25 ratio of maintainability-related to functional problems" | Category enum (core split, cross-domain stability) | adopt/reference |
| Bacchelli & Bird (2013), *Expectations, Outcomes, and Challenges of Modern Code Review* (ICSE) | Reviews are "less about defects than expected": knowledge transfer, team awareness, alternative solutions | Phase 2/3 framing (review intent, not just defect type) | adopt/reference |

| Conventional Comments | Practitioner convention: `<label> [decorations]: <subject>` with labels like `issue`, `suggestion`, `question`, `nitpick`, `praise` and decorations like `(blocking)`, `(non-blocking)` | Category enum (intent labels); severity orthogonal to category | differentiate |

**Notes**

**Direct answer.** Use one domain-neutral core taxonomy with per-lens extensions — the evidence is decisive. The 75:25 maintainability-to-functionality split *replicates across languages, companies, and OSS vs. industry* (Mäntylä & Lassenius on C/C++ and Java; Beller et al. on OSS projects), which means the bulk of review comments fall into categories that are not domain-specific: correctness, security, testing, documentation, style, performance, error-handling, maintainability, dependencies. A stable core keeps cross-repo aggregation (reviewer fingerprints across repos, team comparisons) possible. But the core alone cannot drive Phase 4 blind-spot detection, because a blind spot is only meaningful against a *named, on-domain* best practice ("no review ever touches the IPC boundary"), so each lens adds domain categories (e.g., `ipc-boundary`, `capability-scoping`, `webview-security` for desktop).

**On Conventional Comments:** adopt its separation of concerns, not its label set. Its labels encode *intent and severity* (`question`, `nitpick`, `(blocking)`), which Tricorder should treat as orthogonal metadata, not categories — a nitpick and a blocker can both be about `security`. Mixing intent into the category enum would double the enum and blur Phase 4 aggregation.

**Recommended core (used verbatim in both YAML lenses, marked `core: true`):** `correctness`, `security`, `testing`, `documentation`, `style`, `performance`, `error-handling`, `maintainability`, `dependencies`, `other`. The old dbt-specific entries (`grain`, `incremental`, `source-freshness`, `exposure-contract`, `macro-complexity`) become per-lens extensions of the analytics lens; twelve of them have no meaning elsewhere, which is exactly the bug pattern observed on Berd.

## Q6

**Question:** thresholds/margins before committing to a label; expressing "unknown" or "mixed"; composite vs. per-path vs. primary-plus-secondary lenses; post-selection verification.

| Entry | What it is | Tricorder concept overlap | Verdict |
|---|---|---|---|
| Linguist aggregation | Whole-repo byte percentages per language; no confidence score, no abstention — always emits a breakdown | Detection confidence (contrast case) | differentiate |
| go-enry | Same model as Linguist, embeddable | Detection confidence | differentiate |
| Backstage multi-component model | One repo can host several typed components (`subcomponentOf`, multiple `catalog-info.yaml` locations); identity comes from declarations, not scoring | Mixed-repository handling | adopt/reference |
| CODEOWNERS (GitHub) | Per-path ownership declarations that route review requests; evidence that per-path partitioning of one repo is an accepted primitive | Per-path lens/file_tags; review_path_check | adopt/reference |
| Published thresholds for repository-archetype classification | none found | Detection confidence | ignore |

**Notes**

**Direct answer.** No published classifier — Linguist included — exposes a confidence threshold or an "unknown" label for this problem; Linguist always emits a breakdown and leans on maintainer overrides to correct errors. The honest conclusion is that Tricorder's threshold scheme is a *design decision*, not an adopted standard, and should be calibrated empirically. The recommended scheme (encoded in `detection-rubric.yaml` and each lens's `detection:` block):

1. **Score** per lens from positive signals and counter-signals, after applying the global `ignore_for_detection` list.
2. **Abstain** below `min_score`: report `unknown` and run no lens rather than a wrong lens — a wrong lens produces confidently wrong findings (the Berd/dbt failure), an abstention costs nothing but a message.
3. **Report "mixed"** when the top two scores differ by less than `min_margin`: attach the runner-up's axes as a secondary section in Phase 4 rather than blending lenses.
4. **Never composite lenses.** Blending two authority lists re-introduces off-domain citations — the exact failure mode being removed. Per-path nuance belongs in `file_tags` (which Tricorder already shows the LLM per comment), not in merged rubrics. This mirrors Backstage (several typed components per repo, declared not averaged) and CODEOWNERS (per-path routing).
5. **Post-selection verification** (both checks must pass before paying for synthesis):
   - *Composition check:* observed language bytes must be consistent with `languages_expected` and must not contain `languages_unexpected` above ~5% of bytes. Linguist's own exclusion rules mean SQL doesn't even appear in stats unless present as real source, so a >5% SQL share against a non-SQL lens is a strong wrong-lens signal.
   - *Review-path check:* at least `min_share_of_comments_on_tagged_paths` of historical inline comments must fall under paths the lens's `file_tags` recognize. Reviewers vote with their comments; a lens that can't tag 70% of them is the wrong lens regardless of what the file tree says.

## Open gaps

1. **No published thresholds exist for repository-archetype classification.** `min_score: 10`, `min_margin: 5`, and the 0.7 review-path share are engineering choices, not adopted standards. What would settle it: replaying the rubric over a labeled corpus of ~100 diverse public repos and choosing thresholds that maximize correct selections while keeping abstentions cheap. Until then, ship `status: experimental` and let Tricorder promote lenses after observed accuracy, per the schema.
2. **Berd's `src-tauri/capabilities/` and `deny.toml` are unconfirmed.** The root listing in Part 3 was truncated, and `src-tauri/` contents were not enumerated. The lens does not assume them (no score depends on `capabilities/*.json`; cargo-deny is a conditional gate). What would settle it: one pass over the repo tree API. If cargo-deny/cargo-audit are genuinely absent, their absence is a legitimate Phase 4 `blind_spot` finding under the `dependency-supply-chain` axis.
3. **No single authoritative `unsafe` standard exists.** The Unsafe Code Guidelines Reference is self-declared "largely abandoned"; the Rustonomicon is the maintained companion but is descriptive, not a checklist. The `unsafe-discipline` axis therefore caps at `rule`, not `deterministic`. What would settle it: an official unsafe-code checklist from the Rust project, or cargo-geiger + `[lints] unsafe_code = "forbid"` adoption patterns becoming standardized.
4. **Biome's React-hooks coverage is partial.** The canonical `rules-of-hooks`/`exhaustive-deps` enforcement still lives in ESLint's React plugin; Biome implements a subset. A team on Biome-only tooling cannot reach `deterministic` on every `react-hygiene` item — the axis caps at `rule` until Biome parity or a complementary ESLint config appears. What would settle it: the Biome project's hook-rule coverage tracking (biomejs.dev) reaching parity.
5. **No primary standard for desktop telemetry/privacy review practice.** The `telemetry-privacy` axis is anchored to the repo's own `TELEMETRY.md` (secondary, repo-specific) plus reviewer judgment. Platform store policies (Apple/Microsoft) govern distribution, not code review. Marked `max_maturity: convention`.
6. **Category enum not empirically re-validated.** The core-plus-extensions recommendation rests on published taxonomies (Mäntylä & Lassenius; Beller et al.), but the new enum has not been run over Berd's actual 471 comments. What would settle it: a Phase 1 dry run measuring the share of comments landing in `other` — if that share exceeds roughly 15%, a category is missing.
7. **IaC review standards for the platform lens.** GitHub Actions hardening, Scorecard, and SLSA are solid for CI/CD and supply-chain axes, but there is no comparable primary standard for reviewing Terraform/Kubernetes change *semantics* (plan review, blast radius). The platform lens deliberately limits its axes to what primary sources support; IaC-semantics axes await a citable authority.
