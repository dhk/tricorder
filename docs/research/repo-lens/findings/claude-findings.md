**Notes**

Direct answer. The accepted practice for determining what a repository is, without executing anything, is the Linguist approach: (1) strip vendored, generated and documentation paths first; (2) classify remaining files by an ordered cascade of filename, shebang, extension, heuristics and a classifier; (3) weight by bytes, not file counts; and (4) let the repository override the tool through `.gitattributes`. Ecosystem is then read from manifests that a build tool *requires* to exist (`Cargo.toml`, `go.mod`, `tauri.conf.json`, `pnpm-workspace.yaml`), not from files that any project may carry (`pyproject.toml`'s `[tool]` table, `package.json` alone, `README.md`). Monorepos are partitioned by the package manager's own workspace declaration, and each member is scored separately. AI-assistant configuration must be removed before scoring because the maintainers of those formats describe them as applicable to any project, and one of them is used by more than 60,000 repositories.

Rationale per verdict.

- Linguist (adopt/reference). Its documentation states the detection order verbatim: "Vim or Emacs modeline, commonly used filename, shell shebang, file extension, XML header, man page section, heuristics, naïve Bayesian classification." Files that are binary, vendored, generated, documentation, or of `data`/`prose` type are removed before statistics, and "The percentages are calculated based on the bytes of code for each language." Tricorder should run the same preprocessing before scoring and should treat the GitHub languages API as the already-cleaned byte histogram. The `.gitattributes` overrides are the sanctioned way for a repository to correct the tool (`linguist-vendored`: "Excluded from stats"; `linguist-generated`: "Excluded from stats, hidden in diffs"); Tricorder should honor them. `vendor.yml` and `documentation.yml` give the concrete path lists; note that `vendor.yml` includes `(^|/)\.github/`, which is a maintainers' statement that CI scaffolding is not repository content. `documentation.yml` lists `README`, `CHANGELOG`, `CONTRIBUTING`, `LICENSE`, `docs/`, `examples/`, `samples/`, which is why the rubric's ignore list drops those files from archetype scoring.
- scc (differentiate). It is a comparable tool: extension map, `#!` detection for extensionless files, `--remap-unknown`, and identification of minified/generated files by average line length (`>= 255` bytes). Tricorder does not need to count lines; the useful borrowed idea is the generated-file heuristic, which Linguist also has.
- Cargo, pnpm, npm workspaces, Turborepo (adopt/reference). Cargo: "A workspace is a collection of one or more packages, called workspace members, that are managed together," with `members` supporting globs and a single `Cargo.lock` at the root. pnpm: the file defines "the root of the workspace" and "The root package is always included." npm: "Workspaces are usually defined via the `workspaces` property of the `package.json` file." Turborepo: "there must be a `package.json` to make the package discoverable to your package manager and `turbo`," and the recommended split is `apps/` for applications and services, `packages/` for libraries and tooling. Together these say: the authoritative partition of a polyglot monorepo is the package manager's declared member list, and each member is a unit that can be scored on its own. Berd carries both `pnpm-workspace.yaml` and `crates/`, so it can be partitioned into JS packages and Cargo members.
- `go.mod` (adopt/reference, low weight). "A module is defined by a UTF-8 encoded text file named `go.mod` in its root directory." It identifies the ecosystem but says nothing about what the module is.
- `pyproject.toml` (differentiate). The spec says the `[tool]` table "is where any tool related to your Python project, not just build tools, can have users specify configuration data," and "Tools should not require the existence of the `[build-system]` table." A `pyproject.toml` therefore does not prove a Python package exists; it is a weak signal.
- Tauri project structure and configuration reference (adopt/reference). "the JavaScript project is at the top level, and the Rust project is inside `src-tauri/`"; `tauri.conf.json` is described as the marker file for the Tauri CLI; `capabilities/` is "the folder where capability files are stored." The configuration reference lists the three config file names and the per-platform merged files (`tauri.linux.conf.json`, `tauri.windows.conf.json`, `tauri.macos.conf.json`, and mobile). These are the near-definitive signals in the desktop lens.
- Biome domains (adopt/reference). Domains "can be automatically enabled when Biome detects certain dependencies in your `package.json` file," for example React when `react >=16.0.0` is a dependency. This is a maintainers' precedent for framework fingerprinting from declared dependencies rather than from file globs; Tricorder can read `package.json` dependencies the same way for a second-order signal (React, Playwright, Vitest) without executing anything.
- AGENTS.md, CLAUDE.md, Cursor rules (adopt/reference, as ignore evidence). agents.md describes the file as "a README for agents" and states it is "used by over 60k open-source projects." The Claude Code docs say a project `CLAUDE.md` holds "build and test commands, coding standards, architectural decisions" for "anyone working on the project," can live at `./CLAUDE.md`, `./.claude/CLAUDE.md`, subdirectories, or `CLAUDE.local.md`, and that `/init` reads `.cursor/rules/`, `.cursorrules`, `.github/copilot-instructions.md`, `AGENTS.md`, `.devin/rules/`, `.windsurf/rules/`, `.windsurfrules` and `.clinerules`. Cursor stores project rules in `.cursor/rules` and also reads `AGENTS.md`. None of these documents claims the file indicates a repository's purpose. The rubric therefore ignores all of those paths for every lens. The current Tricorder weights (`CLAUDE.md` +6, `**/agents/**` +5 toward `agent-engineering`) are contradicted by the maintainers' own descriptions.
- OpenSSF Scorecard Security-Policy (adopt/reference, as ignore evidence). `SECURITY.md` is a check ("Verifies published vulnerability reporting policy") that any project is expected to pass; its presence says the project has a disclosure policy, not that the project is a security tool. Tricorder's +8 toward `security` is wrong for the same reason as `CLAUDE.md`.
- GitHub topics (ignore). Topics are admin-chosen, capped at 20, and "GitHub analyzes public repository content and generates suggested topics that repository admins can accept or reject." They are neither content-derived by Tricorder nor reliable, and private repositories get none.
- Nx (none found). Both `nx.dev/concepts/inferred-tasks` and `nx.dev/docs/concepts/inferred-tasks` returned 404 during this pass. Turborepo's documentation covers the same partitioning principle, so nothing depends on Nx.

**Notes**

Direct answer. Tricorder's five-way partition is defensible as a *family* level but not specific enough at the level where review concerns diverge. Every published taxonomy that is used to route work (Backstage), to describe what a package is (crates.io, PyPI), or to compare repositories empirically (Borges et al.) distinguishes *applications* from *libraries* from *tools*, and applications by *environment* (console, web, desktop GUI). None of them has an "agent engineering" or "security" bucket as a top-level type; those are what a component *does*, not what kind of artifact it is. `product-engineering` is therefore too broad: it spans a desktop GUI app, a mobile app, a backend HTTP service, an SDK, and a CLI, which the registries and Backstage all keep apart. The recommended split is sub-profiles under `product-engineering`: `product-engineering-desktop`, `product-engineering-mobile`, `product-engineering-web-frontend`, `product-engineering-backend-service`, `product-engineering-library-sdk`, `product-engineering-cli`. `analytics-engineering` and `platform-engineering` stay as families. `security` and `agent-engineering` should be reconsidered as *secondary* overlays (a security tool is still a CLI or a library; an agent framework is still a library or a service) rather than as top-level archetypes; the two dedicated files in this pass do not attempt them.

Where `block/berd` lands: `product-engineering-desktop`. It is "a desktop app for getting work done with any model" (GitHub description), its Rust half lives in `src-tauri/` (Tauri's desktop layout), it carries Swift, Objective-C and PowerShell for platform integration and a `distro/` packaging directory, and 435 of 471 inline review comments fall under `src/` (267) and `src-tauri/` (168), the two halves of a web-view-over-native-core application. In Borges et al.'s terms it is "Application software: systems that provide functionalities to end-users, like browsers and text editors." In PyPI's terms it would be `Environment :: MacOS X` / `Win32 (MS Windows)` / `X11 Applications`, not `Console` or `Web Environment`. In crates.io terms it is `gui`. The companion `bb-cli/` (26 comments) is a secondary `product-engineering-cli` surface, handled by the file-tag `companion-cli` and by the primary-plus-secondary rule in the rubric rather than by a separate lens.

Rationale per verdict.

- Backstage (adopt/reference). The descriptor format lists Component types "service, website, library" as well-known values and says "The software catalog accepts any type value, but an organization should take great care to establish a proper taxonomy for these." This is the closest thing to an industry-standard software-catalog taxonomy; it confirms that artifact kind (service vs library vs website) is the primary axis.
- Borges et al. 2016 (adopt/reference). The paper classified 2,500 repositories manually into "Application software", "System software", "Web libraries and frameworks", "Non-web libraries and frameworks", "Software tools", and "Documentation"; the authors note that "GitHub does not include information about the application domain of a project," which is why classification had to be manual and content-based. This is the peer-reviewed precedent both for a small artifact-kind taxonomy and for the observation that no metadata field supplies it.
- Munaiah et al. 2017 (differentiate). reaper scores repositories on evidence-of-engineering "dimensions" to separate "engineered software projects" from noise. It is not an archetype taxonomy, but its idea of a score with a threshold, rather than a winner-takes-all label, is the right model for Tricorder's abstention rule (Q6).
- crates.io categories and PyPI Environment classifiers (adopt/reference). crates.io's `command-line-utilities` (30,509 crates), `gui` (4,320), `web-programming` (14,670), `development-tools` (32,130), `api-bindings`, `os`, `database`, `network-programming`, `games`, `text-editors`, `emulators` are the registry's own vocabulary for what a crate is; PyPI's `Environment :: Console` vs `Web Environment` vs `X11 Applications` / `MacOS X` / `Win32` is the same distinction by runtime environment. These are the accepted splits that `product-engineering` should be broken along.
- SLSA and Scorecard (differentiate). SLSA "classifies intended users rather than project types" and describes levels of build integrity; Scorecard's documentation explicitly acknowledges "some projects cannot meet this requirement" and does not type projects. Both belong in the platform lens as *authorities*, not in the taxonomy.
- GitHub topics (ignore). See Q1.

Direct answer, part 2 (vocabulary). No published source uses Tricorder's five words, but three published practices map onto the ladder closely enough that Tricorder should keep its vocabulary and cite the mapping rather than adopt a foreign one:

- Google's Tricorder paper is the strongest precedent for the top of the ladder. An analyzer is admitted to code review only if "The warning should be easy to understand and the fix should be clear," "The warning should have very few false positives. Developers should feel that we are pointing out an actual issue at least 90% of the time," and it "has the potential for significant impact"; analyzers whose "Not useful" click rate reaches 10% are turned off. The 2018 case study adds the two-tier structure that matches `rule` vs `deterministic`: pre-commit checks "where a failure requires an explicit override by the developer to enable a commit" versus "automated code analyses through Tricorder that may not block committing a change." So `deterministic` should mean "enforced as a blocking check," and a warning-only analyzer sits at `rule`.
- Clippy's category levels (`deny`, `warn`, `allow`) and Biome's recommended/nursery split are per-rule ladders inside the tools: a lint at `allow` is available but not enforced (`guidance`), at `warn` it is surfaced but non-blocking (`rule`), at `deny` it fails the build (`deterministic`). This is the concrete meaning of "ready to move up the ladder" for a Rust or TypeScript pattern: enable the lint, then raise its level.
- GitHub protected branches and lefthook are the mechanisms that make a check blocking: "all required status checks must pass before collaborators can merge changes into the protected branch." Scorecard's checks (Branch-Protection, CI-Tests, SAST, Pinned-Dependencies, Token-Permissions) are an external, automated audit of whether those mechanisms are in place, and are a reasonable Phase 4 cross-check for the platform lens.
- DORA (differentiate) names capabilities (continuous integration, test automation, streamlining change approval) but its catalog page "does not define a maturity ladder or levels"; it is useful as a vocabulary for *what* to institutionalize, not for the steps. CMMI (ignore): its five organizational levels concern process management, not per-practice enforcement, and only secondary sources were reachable (Wikipedia and vendor pages; the CMMI Institute site was not fetched), so it is not adopted.

**Notes**

Direct answer. Tricorder should use one domain-neutral core taxonomy with per-lens extensions, not a fully per-lens enum. The evidence:

1. The two peer-reviewed defect taxonomies for review findings are domain-neutral by construction and were validated across languages and settings. Mäntylä and Lassenius built theirs from 388 industrial C/C++ and 371 student Java findings, found that "75 percent of defects found during the review do not affect the visible functionality," and split findings into functional and evolvability, the latter into documentation, visual representation, and structure. Beller et al. took the same scheme to two open-source Java projects (ConQAT, GROMACS) and report "the reported 75:25 distribution of maintainability versus functional changes holds in our OSS systems, too." Bosu et al. reused it again at Microsoft to rate usefulness. A taxonomy that has been reused three times across C/C++, Java, industrial and OSS settings is exactly what the core should be; it would apply unchanged to Berd's Rust and TypeScript comments.
2. Bacchelli and Bird's card sort adds the categories that are not defects at all but dominate real comment streams: *understanding* (questions), *social communication*, *knowledge transfer*, and "code improvements" (29%, the largest bucket: better practices, unused code, readability) versus "defects" (14%, "mostly address 'micro' level and superficial concerns"). A core enum without a `question` category would misfile the most frequent kind of comment as `other`, which is the resolution loss the brief describes.
3. Domain-specific concerns are real but sit *inside* those buckets: an IPC-scoping comment is a functional/interface or check defect; an effect-dependency comment is a functional/logic defect; a SAFETY-comment request is an evolvability/documentation defect. Making them per-lens *extensions* keeps the Phase 2 and Phase 3 fingerprints comparable across lenses (a reviewer's functional-vs-evolvability ratio is meaningful in any domain) while giving Phase 4 the specific names it needs for blind-spot detection.

Concretely, the core placed identically in both lens files (marked `core: true`) is: `functional-defect`, `design-structure`, `naming`, `documentation`, `style`, `testing`, `error-handling`, `performance`, `security`, `dependency-supply-chain`, `process`, `question`, `other`. Mapping to the literature: `functional-defect` is Mäntylä's functional group; `design-structure` is structure/organization/solution approach and Google's Design and Complexity; `naming` and `documentation` are the documentation group (textual, naming) and Google's Naming and Comments; `style` is visual representation and Google's Style/Consistency; `testing` is Google's Tests and Bacchelli's testing category; `question` is Bacchelli's understanding; `process` and `other` absorb social communication, review-tool and misc. `error-handling`, `performance`, `security` and `dependency-supply-chain` are added because every authority set in Q3 has a distinct section for each and because reviewers in both lenses write them; they are sub-types of functional defects that are worth keeping separate for Phase 4.

Conventional Comments (differentiate) classifies *intent and blocking status*, not topic: "suggestion", "issue", "nitpick", "question", with "(blocking)"/"(non-blocking)". That is orthogonal to the category enum and closer to Tricorder's `maturity` and to Phase 2's "review style." Tricorder should not fold these labels into `category`; if it wants them, they belong in a separate `intent` field. `question` is the one label that also appears in Bacchelli's taxonomy and is therefore kept in the core.

**Notes**

Direct answer, thresholds. The established formalism is Chow's reject option and its modern form, selective classification: a classifier that "trade[s] off classifier coverage for higher accuracy" by refusing to label inputs whose confidence falls below a threshold. The threshold is chosen for a target risk, not for a target coverage, which is the right orientation for Tricorder: a wrong lens is expensive, an abstention is cheap. Tricorder's current detector has no reject region (sum of weights, highest wins, no threshold, no "unknown"), so its coverage is 100% and its error rate is whatever the weights produce; the Berd case shows that error rate is nonzero on the very first production test. The rubric introduces two thresholds: `min_score` (absolute confidence; below it, outcome `unknown`) and `min_margin` (lead over the runner-up; below it, outcome `mixed`). Margin over the runner-up is the score-based analogue of Chow's rule on the maximum posterior; with hand-set weights rather than calibrated probabilities there is no principled constant, so the values 10 and 5 are set so that a single strong manifest (`tauri.conf.json` at 10) clears `min_score` alone while a pile of weak two-point signals does not, and so that two families cannot be separated by one weak file.

Direct answer, "unknown" and "mixed." Linguist's behavior is the accepted reference for expressing composition rather than committing to a label: it publishes a byte-weighted histogram and silently drops files it cannot classify; it never emits a single "this repository is X." Tricorder should do the same at the reporting layer: always show the top candidates with their matched signals, and treat the selected lens as a decision made *on top of* that histogram, revocable by the post-selection checks.

Direct answer, multi-archetype repositories. I found no peer-reviewed comparison of composite, per-path, and primary-plus-secondary lenses for downstream review judgment (`none found` row); the recommendation is therefore drawn from tool precedents. Three of them argue for primary-plus-secondary with per-path tagging over a composite: CODEOWNERS routes each path to its owner with last-match precedence rather than merging owners into one; Biome enables the React, Playwright and Test domains independently, each on its own evidence, in the same project; and Cargo, pnpm and npm all define a monorepo as a list of members that can be scored one at a time. A composite lens would blend authority lists and Phase 4 absence findings across domains, which reintroduces the failure this research exists to remove (a service lens's blind spots reported against a desktop app). A pure per-path lens would fragment the reviewer fingerprints for people who work across the boundary, and Berd's histogram shows reviewers do (170 `.rs` and 262 `.ts`/`.tsx` comments from 18 contributors). The rubric therefore selects one primary lens (categories, axes, authorities, prompt context, Phase 4 blind spots) and allows a secondary lens to contribute only file tags, extra Phase 1 categories on the paths it covers, and its `must_not` list, when it scores above its own `min_score` and covers at least 15% of comment paths the primary does not tag. For Berd, `bb-cli/` (26 of 471 comments, 5.5%) falls below that bar, so the CLI is handled by a file tag inside the desktop lens rather than by a second lens.

Direct answer, post-selection verification. Before synthesis: (1) composition check against the languages API: any `languages_unexpected` above 5% of bytes flags the selection (a Rust/TypeScript desktop lens should never be chosen for a repository with substantial SQL or HCL); (2) review-path check: at least 70% of inline comment paths must match a lens `file_tags` glob (for Berd, 471 of 471 do); (3) counter-signal report: any matched counter-signal is shown next to the selection; and after synthesis (4) smoke check: none of the lens's forbidden strings ("grain", "fact model", "dbt", "SQLFluff", "Kimball") may appear in any phase output, otherwise the run is invalid. Checks 1 and 2 use data Tricorder already has (the languages API and the harvested comments), so they cost nothing.
